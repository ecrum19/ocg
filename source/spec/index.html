This document defines a practical usage specification for https://w3id.org/vord# (VoRD), a vocabulary for describing operational restrictions of SPARQL services. It is written primarily for SPARQL endpoint maintainers who need to publish rate limits, result-size limits, timeouts, quotas, concurrency limits, load-shedding behavior, and related HTTP signals in a machine-readable form that users and query engines can discover.

VoRD extends SPARQL Service Description by treating endpoint restrictions as service features linked from an sd:Service. The goal of this specification is to make those descriptions predictable enough that automated clients can choose endpoints, plan query batches, avoid known limits, and respond correctly when a limit is reached.

This is an unofficial draft. It is a vocabulary usage specification, not the definitive ontology publication for the VoRD namespace. Normative requirements in this document are intended to define a publishable maintainer profile for VoRD data.

Introduction

Public SPARQL endpoints commonly enforce operational limits: requests per minute, execution deadlines, maximum result sizes, per-client quotas, concurrency ceilings, or temporary throttling under load. These limits are often documented only in human-readable prose. That is not sufficient for federated query engines, crawlers, batch clients, or monitoring tools that need to adapt before sending work to an endpoint.

SPARQL Service Description already defines a discovery mechanism and a vocabulary for describing SPARQL services. In particular, a service can be represented as sd:Service, linked to its endpoint with sd:endpoint, and linked to features with sd:feature [[SPARQL11-SERVICE-DESCRIPTION]]. VoRD reuses that model by defining vord:hasRestriction as a service-to-restriction property and as a subproperty of sd:feature.

The examples in this specification use Turtle, a compact concrete syntax for RDF graphs [[TURTLE]]. The validation profile is expressed in SHACL, which is a language for describing and validating RDF graphs [[SHACL]].

Scope

This specification covers how to publish VoRD descriptions for SPARQL endpoints. It does not define server-side rate-limiting algorithms, require a particular SPARQL implementation, or require endpoint operators to reveal sensitive internal capacity data. Where exact internal values are operationally sensitive, publishers can disclose conservative public thresholds, advisory limits, or load-dependent behavior.

A VoRD description is about operational behavior visible to clients. It should describe the effective limit that a well-behaved client can rely on, rather than every internal limiter, proxy, firewall, or scheduler rule that may contribute to enforcement.

Terminology

The key words MUST, MUST NOT, REQUIRED, SHOULD, SHOULD NOT, RECOMMENDED, MAY, and OPTIONAL in this document are to be interpreted as described in RFC 2119 and RFC 8174 when, and only when, they appear in all capitals, as shown here.

VoRD publisher
An endpoint maintainer, documentation maintainer, or automated deployment process that publishes VoRD RDF for a SPARQL service.
VoRD consumer
A user agent, query engine, crawler, client library, catalog, or monitoring system that reads VoRD RDF to understand endpoint restrictions.
restriction
A resource typed vord:Restriction that states a measurable operational threshold and the way the endpoint enforces that threshold.
hard restriction
A restriction whose threshold is intended to be strictly enforced. It is represented with vord:hardRestriction true.
advisory restriction
A published threshold that is approximate, load-dependent, or guidance-only. It is represented with vord:hardRestriction false.

Conformance

A conforming VoRD publisher satisfies all normative requirements in this document that are addressed to publishers. A conforming VoRD consumer satisfies all normative requirements in this document that are addressed to consumers.

A VoRD publisher MUST publish RDF that conforms to the data model in and the maintainer profile in . A VoRD publisher SHOULD validate the published RDF with the SHACL shapes summarized in before deployment.

A VoRD consumer MUST NOT assume that a missing restriction means that no corresponding operational limit exists. Missing VoRD data only means that the publisher did not advertise that limit in the VoRD description.

Publishing Model

Discovery

A VoRD publisher SHOULD include VoRD triples in the SPARQL service description returned by dereferencing the endpoint IRI with HTTP GET and no query parameters. This follows the SPARQL Service Description discovery pattern, which expects an RDF service description at the endpoint and recommends content negotiation for RDF representations [[SPARQL11-SERVICE-DESCRIPTION]].

A VoRD publisher MAY also publish the same VoRD graph at a documentation URL, dataset catalog URL, or VoID/DCAT metadata URL, but that alternative publication SHOULD NOT replace service-description discovery unless endpoint-level discovery is impossible.

Core graph pattern

A VoRD service description MUST include an sd:Service resource with an sd:endpoint IRI. The service resource MUST link to one or more restrictions using vord:hasRestriction. 

@prefix sd:   <http://www.w3.org/ns/sparql-service-description#> .
@prefix vord: <https://w3id.org/vord#> .

<https://example.org/sparql#service> a sd:Service ;
  sd:endpoint <https://example.org/sparql> ;
  vord:hasRestriction <https://example.org/sparql#rateLimit> .

<https://example.org/sparql#rateLimit> a vord:Restriction, vord:RateRestriction .

Each restriction MUST be typed as vord:Restriction and as exactly one standard restriction subclass from VoRD, unless it is an extension restriction as described in .

Restriction identifiers

Restriction resources SHOULD have stable IRIs. Stable IRIs make it possible for documentation, monitoring systems, cached service descriptions, and issue reports to refer to the same operational policy over time. Blank nodes MAY be used for temporary or generated descriptions, but they are not recommended for public endpoint metadata.

Maintainer Restriction Profile

This section defines the minimum properties that make a restriction actionable for users and query engines.

Common requirements

Each standard VoRD restriction MUST include the following properties exactly once:

  • vord:metric, identifying the measured quantity.
  • vord:maxValue, an xsd:integer threshold.
  • vord:hasScope, identifying the subject of enforcement.
  • vord:enforcement, identifying the action taken when the threshold is reached.
  • vord:hardRestriction, an xsd:boolean indicating whether the threshold is strict.

If the unit is not obvious from the metric, the restriction MUST include vord:unit. Publishers SHOULD use QUDT unit IRIs such as unit:COUNT, unit:SEC, unit:PERCENT, and unit:ONE for dimensionless cost scores [[QUDT-UNITS]].

Publishers SHOULD include vord:returnsStatusCode and vord:httpSignalHeader when clients can use HTTP status codes or headers to respond to the restriction. For rate-limit rejections, 429 is the HTTP status code for too many requests and may be accompanied by a Retry-After header [[RFC6585]]. HTTP semantics, including status code and header behavior, are defined by RFC 9110 [[RFC9110]].

Priority profile for endpoint maintainers

A public endpoint that wants basic machine-readability MUST publish the restrictions that are both enforced and externally meaningful. The following priority profile is recommended for incremental adoption.

Priority Restriction types Maintainer guidance
Baseline vord:RateRestriction, vord:ResultSizeRestriction, vord:ResponseTimeRestriction Publish these first because they most directly affect query batching, timeout selection, pagination, and retry behavior.
Recommended vord:ConcurrentRequestsRestriction, vord:QuotaRestriction Publish when clients can reduce parallelism or schedule work over longer periods.
Advanced vord:ServerLoadRestriction, vord:CostModelRestriction Publish when load- or cost-based behavior is stable enough to explain, or when an implementation-specific model is part of endpoint admission control.

Scope guidance

The scope tells clients who or what is counted. A publisher MUST choose the most specific accurate scope. For example, use vord:PerClientIP for an IP-based limiter, vord:PerAPIKey for a key-based limiter, vord:PerUser for authenticated user identity, vord:PerRequest for a single query execution, and vord:GlobalScope for a limit shared by all traffic.

If the limiter uses a different identity function, such as User-Agent plus IP address, the publisher MAY mint a custom scope IRI. Custom scopes MUST be typed vord:Scope and SHOULD have skos:prefLabel and dcterms:description.

Enforcement guidance

The enforcement mode tells clients what happens at the threshold. Publishers MUST choose the enforcement mode that describes the externally visible behavior. Use vord:RejectRequest when requests fail at or above the threshold, vord:TruncateResult when partial results are returned, vord:QueueRequest when requests are delayed, vord:ThrottleResponse when processing or delivery is slowed, and vord:DegradeQuality when the service responds with reduced quality or partial capability.

Freshness and operational truth

A VoRD publisher MUST keep machine-readable restrictions synchronized with the effective public policy. If a limit changes, the VoRD description SHOULD be updated in the same deployment or documentation release as the actual limiter. Publishers SHOULD use dcterms:modified or another metadata property on the service description graph to help consumers assess freshness.

A publisher MUST set vord:hardRestriction false when a threshold is only a recommendation, when it is load-dependent, or when it may vary without prior notice. Consumers SHOULD treat advisory restrictions as planning hints rather than guaranteed behavior.

Implementation Guidance for SPARQL Endpoint Maintainers

Recommended implementation steps

  1. Inventory all externally meaningful limits: rate windows, result truncation, query timeout, concurrency, quotas, load shedding, and cost-based admission.
  2. Decide the public service IRI and make sure it has an sd:endpoint triple.
  3. Create one restriction resource per independent limit. Do not collapse unrelated limits into one resource.
  4. Use standard VoRD metrics, scopes, and enforcement modes whenever they match the deployed behavior.
  5. Add units, windows, HTTP status codes, and retry hints so clients can act without scraping prose documentation.
  6. Validate the graph with SHACL, publish it through service-description discovery, and monitor it for drift against production configuration.

HTTP signals

A VoRD publisher SHOULD align published HTTP signals with actual endpoint behavior. For a rate limiter that returns 429 and Retry-After, publish both vord:returnsStatusCode "429"^^xsd:integer and vord:httpSignalHeader http:retry-after. If the server may also return 503 during backend overload, publish that as a separate load or concurrency restriction rather than overloading the rate restriction.

Result truncation

When a result-size limit causes partial results, the restriction MUST use vord:TruncateResult. When a result-size limit rejects the request before execution or fails the query, use vord:RejectRequest. Publishers SHOULD document, using dcterms:description, whether truncation is visible through a warning, a status code, or response metadata.

Dynamic or load-dependent limits

For dynamic server behavior, publish the stable public policy rather than a rapidly changing internal metric. If an endpoint degrades under load without a fixed threshold, use vord:ServerLoadRestriction, set vord:hardRestriction false, and describe the behavior in prose with dcterms:description.

Extensions

Publishers MAY mint extension metrics, scopes, cost models, and restriction subclasses when the standard VoRD terms do not precisely describe deployed behavior. Extension metrics MUST be typed vord:Metric. Extension scopes MUST be typed vord:Scope. Extension restriction classes SHOULD be declared as subclasses of vord:Restriction.

Extension terms SHOULD include human-readable labels and descriptions. Consumers that do not recognize an extension term SHOULD still process the common VoRD properties on the restriction resource.

Consumer Guidance

VoRD consumers can discover restrictions by querying a service description graph for vord:hasRestriction. The following query returns the core fields that a query engine usually needs for scheduling and endpoint selection. 

PREFIX sd:   <http://www.w3.org/ns/sparql-service-description#>
PREFIX vord: <https://w3id.org/vord#>

SELECT ?endpoint ?restriction ?restrictionType ?metric ?maxValue
       ?unit ?windowDuration ?scope ?enforcement ?hardRestriction
WHERE {
  ?service a sd:Service ;
           sd:endpoint ?endpoint ;
           vord:hasRestriction ?restriction .
  ?restriction a vord:Restriction ;
               a ?restrictionType ;
               vord:metric ?metric ;
               vord:maxValue ?maxValue ;
               vord:hasScope ?scope ;
               vord:enforcement ?enforcement ;
               vord:hardRestriction ?hardRestriction .
  FILTER(?restrictionType != vord:Restriction)
  OPTIONAL { ?restriction vord:unit ?unit . }
  OPTIONAL { ?restriction vord:windowDuration ?windowDuration . }
}
ORDER BY ?endpoint ?restriction

Consumers should use vord:hardRestriction to distinguish strict limits from hints, should respect vord:retryAfterHint and HTTP Retry-After signals where present, and should fall back to conservative defaults when a service description is missing or incomplete.

Examples

Basic service description

This example advertises a per-IP request rate, a result-binding limit, and a per-request response-time limit. 

@prefix ex: <https://example.org/sparql/> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .
@prefix sd: <http://www.w3.org/ns/sparql-service-description#> .
@prefix vord: <https://w3id.org/vord#> .
@prefix unit: <http://qudt.org/vocab/unit/> .
@prefix http: <http://www.w3.org/2011/http-headers#> .

ex:service a sd:Service ;
  sd:endpoint <https://example.org/sparql> ;
  sd:supportedLanguage sd:SPARQLQuery ;
  sd:feature sd:BasicFederatedQuery ;
  vord:hasRestriction ex:rateRestriction, ex:resultRestriction, ex:responseTimeRestriction .

ex:rateRestriction a vord:Restriction, vord:RateRestriction ;
  vord:metric vord:requestsPerWindow ;
  vord:maxValue "60"^^xsd:integer ;
  vord:burstValue "15"^^xsd:integer ;
  vord:unit unit:COUNT ;
  vord:windowDuration "PT1M"^^xsd:duration ;
  vord:hasScope vord:PerClientIP ;
  vord:enforcement vord:RejectRequest ;
  vord:hardRestriction "true"^^xsd:boolean ;
  vord:returnsStatusCode "429"^^xsd:integer ;
  vord:retryAfterHint "PT30S"^^xsd:duration ;
  vord:httpSignalHeader http:retry-after .

ex:resultRestriction a vord:Restriction, vord:ResultSizeRestriction ;
  vord:metric vord:resultBindings ;
  vord:maxValue "50000"^^xsd:integer ;
  vord:unit unit:COUNT ;
  vord:hasScope vord:PerRequest ;
  vord:enforcement vord:TruncateResult ;
  vord:hardRestriction "true"^^xsd:boolean .

ex:responseTimeRestriction a vord:Restriction, vord:ResponseTimeRestriction ;
  vord:metric vord:evaluationTime ;
  vord:maxValue "600"^^xsd:integer ;
  vord:unit unit:SEC ;
  vord:hasScope vord:PerRequest ;
  vord:enforcement vord:RejectRequest ;
  vord:hardRestriction "true"^^xsd:boolean ;
  vord:returnsStatusCode "503"^^xsd:integer .

Public endpoint example: Wikidata Query Service

This non-normative example shows how a maintainer could encode selected public Wikidata Query Service limits. The public documentation states that the query runtime on the public endpoint is limited to 60 seconds, that one client has 60 seconds of processing time each 60 seconds, that one client is allowed 30 error queries per minute, that exceeding those limits is throttled with HTTP 429 and Retry-After, and that access is currently limited to 5 parallel queries per IP [[WDQS-USER-MANUAL]].

The processing-time budget is represented with an extension restriction because the current VoRD metric set does not include a standard processing-seconds-per-window metric.

Security and Privacy Considerations

VoRD descriptions can reveal operational thresholds. Publishers should avoid exposing sensitive internal capacity, infrastructure topology, or abuse-detection details that would make it easier to attack a service. Publishing conservative public thresholds is often preferable to publishing exact internal limits.

Scopes such as vord:PerUser, vord:PerAPIKey, or custom identity scopes describe how traffic is grouped; they should not disclose actual user identifiers, API keys, IP addresses, or other personal data.

Maintainer Checklist

  • Does the service description contain an sd:Service and the correct sd:endpoint?
  • Is every operationally meaningful public limit represented by a separate vord:Restriction?
  • Does every restriction have exactly one metric, maximum value, scope, enforcement mode, and hard/advisory boolean?
  • Are units and window durations explicit where clients need them?
  • Are HTTP status codes and retry headers represented when they are part of real endpoint behavior?
  • Are custom metrics and scopes typed and labelled?
  • Does the RDF pass the VoRD SHACL validation profile?
  • Is the published RDF updated whenever the deployed endpoint policy changes?
